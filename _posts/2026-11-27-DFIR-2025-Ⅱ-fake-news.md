Phần hai của chuỗi DFIR 2025, nối tiếp ngay sau Lost In Router. Ở bài trước, router của công ty bị chiếm và tên miền nội bộ `portal.r3.internal` bị trỏ sang một trang giả trên Netlify. Bài này đi tiếp phía nạn nhân: một nhân viên thấy thông báo "cần cập nhật Chrome", làm theo hướng dẫn, rồi mới nhận ra máy mình làm gì có Chrome.

- Độ khó: **Insane**
- Flag format: `r3ctf{...}`
- Tài liệu giao gồm một memory dump Windows (`dump.raw`) và một file `capture.pcapng`

## Khảo sát ban đầu

Mình bắt đầu bằng `windows.pslist` để xem trong máy có gì bất thường. Có hai tiến trình đáng ngờ ngay từ đầu:

```plaintext
PID   PPID  Name            Create (UTC)          Exit (UTC)
7336  3816  powershell.exe  2025-07-05 12:39:48   2025-07-05 12:40:07
9020  804   chrome.exe      2025-07-05 12:49:07   N/A
```

Đề nói máy không cài Chrome, vậy mà lại có `chrome.exe` đang chạy, chỉ 4 thread, không có tiến trình con nào (Chrome thật luôn kéo theo một đống renderer/gpu process), và tiến trình cha 804 đã biến mất kể cả với `psscan`.

## Q3: Hàm thực thi stage 2

**Đáp án:** `FinalizeUpdateConfig`

Hai file MSI và MST không còn trong Downloads, nhưng Windows Installer luôn giữ bản cache để phục vụ sửa chữa/gỡ cài đặt:

```bash
$ vol -f dump.raw windows.filescan | grep -aiE "\.msi|\.mst"
0xd70a161847f0  \Windows\Installer\14cf38.msi
0xd70a19011a50  \Windows\Installer\{01E5F517-A390-379A-869D-FCDD8884EFF0}\config.mst
```

<img width="940" height="506" alt="image" src="https://github.com/user-attachments/assets/142addc1-0855-4b2c-8842-cccff1b99b60" />

`14cf38.msi` chính là `ChromeInstaller.msi` bị đổi tên ngẫu nhiên khi cache. Dump `config.mst` ra rồi thử `msiinfo tables` thì chỉ thấy `_SummaryInformation` và `_ForceCodepage`. Đây là bản chất của file transform: nó chỉ lưu phần khác biệt so với MSI gốc dưới dạng stream, msitools không đọc thành bảng được. Nhưng string pool thì vẫn đọc được bằng `strings`:

```bash
$ strings -a out/config.mst | grep -iE "Finalize|\.dll"
core.dllFinalizeUpdateConfigDisplayUpdateInfoNOT REMOVERegisterUserRegisterProduct
core.dll
FinalizeUpdateConfig
KERNEL32.dll
...
chrome_elf.dll
KERNEL32.dll
USER32.dll
GDI32.dll
```

<img width="940" height="250" alt="image" src="https://github.com/user-attachments/assets/5fc13011-360d-455c-b68f-ae244486915e" />

Dòng đầu là string pool (các chuỗi nối liền nhau). Ghép vào các cột của bảng `CustomAction`:

```plaintext
Action = DisplayUpdateInfo | Type = DLL | Source = core.dll | Target = FinalizeUpdateConfig
Condition = NOT REMOVE, chèn vào InstallExecuteSequence quanh RegisterUser/RegisterProduct
```

Tức là trong lúc cài Chrome thật, msiexec nạp `core.dll` (nằm trong bảng `Binary` của transform) và gọi hàm export `FinalizeUpdateConfig`. Hai dòng `core.dll` / `FinalizeUpdateConfig` đứng riêng phía sau là bảng export của chính `core.dll`, nên phía gọi và phía được gọi khớp nhau.

Mình trích `core.dll` ra bằng `olefile` (lọc stream có header `MZ`), rồi tìm thêm PE nhúng bên trong nó, cụ thể tại offset `0x2d100`: một file PE khác được nhét sẵn bên trong, nhiều khả năng là malware stage tiếp theo.

Script trích `core.dll`:

```python
import olefile, struct

ole = olefile.OleFileIO("out/config.mst")
for s in ole.listdir():
    data = ole.openstream(s).read()
    if data[:2] == b"MZ":
        core = data
        open("out/core.dll", "wb").write(data)

def valid_pe(d, i):
    lf = struct.unpack_from("<I", d, i + 0x3c)[0]
    return lf < 0x1000 and d[i+lf:i+lf+4] == b"PE\0\0"

i = core.find(b"MZ", 1)
while i != -1 and not valid_pe(core, i):
    i = core.find(b"MZ", i + 1)
print("embedded PE at", hex(i))          # 0x2d100
open("out/embedded.dll", "wb").write(core[i:])
```

**Đáp án:** `T1574.001`

Dump hai bản Chrome ra thì MD5 trùng nhau, và nhìn kỹ tên file dump thì chúng còn trỏ chung một section object (`0xd70a16fdd670`). Thực chất đó là một file: trình cài Chrome giải nén vào `Temp\source...\Chrome-bin\` rồi move sang `Application\`, FILE_OBJECT mang tên cũ chỉ là phần sót lại.

Chrome thật để `chrome_elf.dll` trong thư mục phiên bản `138.0.7204.97\`. Nếu file được nạp nằm ở chỗ khác (ví dụ ngay cạnh `chrome.exe`), hoặc ghi đè bản thật, đó là bằng chứng sideload.

Stage 3 dựa vào cơ chế của Windows chứ không cần khai thác lỗ hổng nào:

- `chrome.exe` thật, có chữ ký Google, luôn nạp `chrome_elf.dll` khi khởi động.
- Windows tìm DLL theo thứ tự, và thư mục của chính exe được ưu tiên đầu tiên.
- Attacker đặt một `chrome_elf.dll` độc ở vị trí sẽ được tìm thấy trước → `chrome.exe` thật tự nạp mã độc vào chính tiến trình của nó. Mã độc chạy dưới "vỏ" một chương trình hợp pháp, nên AV/EDR khó nghi ngờ.

## Q5: Hàm thực thi stage 3

**Đáp án:** `GetInstallDetailsPayload`

- **DllMain**: chạy ngay khi DLL được nạp, nhưng bị giới hạn (loader lock), dễ treo tiến trình.

Đây là hàm bọc (wrapper), chưa phải lõi AES, nhưng nó tiết lộ thứ tự tham số. Đặt lại tên theo vai trò:


Cấu trúc này khớp rất sát với thư viện AES C++ mã nguồn mở phổ biến [SergeyBel/AES](https://github.com/SergeyBel/AES):

```cpp
AES aes(AESKeyLength::AES_128);   // enum: AES_128 = 0, AES_192 = 1, AES_256 = 2
unsigned char *DecryptCBC(const unsigned char in[], unsigned int inLen,
                          const unsigned char key[], const unsigned char *iv);
std::vector<unsigned char> DecryptCBC(std::vector<unsigned char> in,
                                      std::vector<unsigned char> key,
                                      std::vector<unsigned char> iv);
```

- `sub_180001740(v15, 0)` trong `GetInstallDetailsPayload` = constructor `AES(AES_128)` (tham số 0) → AES-128, key 16 byte
- `sub_1800017C0(ctx, in, inLen, key, iv)` = `DecryptCBC` bản con trỏ
- `sub_180002630` là bản vector gọi sang bản con trỏ, giải phóng bộ nhớ rồi trả vector

Suy ra vai trò 2 biến global:

```plaintext

a5 = unk_18003C370 -> IV
```

`unk_18003C358` và `unk_18003C370` cách nhau đúng `0x18` byte, bằng kích thước một `std::vector`/`std::string` trên MSVC x64, nên chúng là hai biến global được khởi tạo lúc DLL nạp (dynamic initializer). Bấm `X` trên từng biến để tìm hàm ghi vào nó, ra `sub_180001000` (key) và `sub_1800010C0` (IV).

## Q8: Thuật toán và key giải mã traffic

**Đáp án:** `aes_ctr_b07c3644328c8ce428c408ceca9ea23038f2f248f87ceeb03e040aaab07c5638`

Framework C2: [Havoc](https://github.com/havocframework/havoc)

Biết là Havoc rồi thì khỏi phải đào sâu trong IDA. Mình biết Havoc Demon mã hóa traffic bằng **AES-256-CTR**, và nó có một điểm yếu kinh điển: key và IV được gửi dạng rõ trong gói đăng ký đầu tiên (`DEMON_INIT`). Cấu trúc gói đó:

```plaintext
[4]   tổng độ dài
[4]   magic        = DE AD BE EF
[4]   agent ID
[4]   command ID   = 0x63 (DEMON_INIT)
[4]   request ID
[32]  AES key      <- đáp án Q8
[16]  AES IV
[...] metadata máy nạn nhân (đã mã hóa bằng key trên)
```

Key chỉ nằm trong request thứ 1 (gói đăng ký `DEMON_INIT`), nhưng trong chall thì mình tìm lại không thấy:

<img width="602" height="321" alt="image" src="https://github.com/user-attachments/assets/0bbfa5e3-4c7e-49ae-a8f4-63fc6ba7dd5d" />

- Gói đầu tiên của pcap đã là ACK của server, không có bắt tay TCP (SYN/SYN-ACK) của kết nối này → pcap bắt đầu giữa chừng, lúc kết nối đã mở sẵn.
- Gói 3 là response cho một request không có trong pcap. Wireshark vẫn đếm request "ma" đó là số 1, nên gói 13 mới là 2/759.
- Request bị thiếu đó chính là gói `DEMON_INIT` chứa key. Response 4 byte ở gói 3 là server trả lời việc đăng ký.

Do đó mình sẽ lấy key từ RAM của `chrome.exe` (PID 9020). Demon giữ key/IV trong bộ nhớ suốt phiên, và buffer gói INIT có thể vẫn còn trong heap. Dump bộ nhớ tiến trình rồi dò mẫu header INIT:

## Q9: MD5 của đoạn PowerShell được thực thi

**Đáp án:** `aa948510c9e99a2a794eb9f93e448be5`

Có key rồi thì viết script giải mã hàng loạt. Vài điểm cần để ý khi làm:

- Havoc reset bộ đếm CTR về IV ở mỗi gói, nên từng gói giải mã độc lập được.
- Phần mã hóa bắt đầu ở offset 12 với gói C2 → nạn nhân (command + request ID + length) và offset 20 với gói nạn nhân → C2.

## Q10: Tên persistence attacker tạo

**Đáp án:** `SecurityUpdate`

**Hướng tiếp cận ban đầu.** Mình tìm dấu vết scheduled task trong memory dump theo hai cách:

1. `windows.filescan` với thư mục `\Windows\System32\Tasks\` — chỉ ra các task mặc định của Microsoft.
2. Registry `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Schedule\TaskCache\Tree` — cho ra một task đáng ngờ là `\GoogleSystem\GoogleUpdater`, tạo lúc 2025-07-05 12:48:48 UTC.

Task này được tạo trước khi implant kết nối C2 (12:49:07), nên nhiều khả năng do stage 2 (`core.dll`) tạo trong quá trình cài MSI, chứ không phải lệnh attacker gửi qua C2.

<img width="940" height="519" alt="image" src="https://github.com/user-attachments/assets/fdd95e67-c1e2-4b0c-ba82-fda5ab657dc1" />

Tiếp theo mình tìm lệnh persistence. Quét keyword (`schtasks`, `Register-ScheduledTask`…) trên toàn bộ traffic đã giải mã không ra kết quả. Mình chuyển sang xét kích thước gói: gói C2 → nạn nhân lớn nhất là **frame 4708 (9770 byte)**, lớn bất thường so với các lệnh shell chỉ vài trăm byte, đúng cỡ của một BOF (Beacon Object File).

<img width="940" height="483" alt="image" src="https://github.com/user-attachments/assets/7c16b5c7-9407-4320-a588-2f707c418d47" />

Mình viết lại 1 script để lọc thêm cả trường `data.data` lẫn `media.type`:

```python
import subprocess, shutil, os, re, base64
from Crypto.Cipher import AES

PCAP = "capture.pcapng"
KEY = bytes.fromhex("b07c3644328c8ce428c408ceca9ea23038f2f248f87ceeb03e040aaab07c5638")
IV = int.from_bytes(bytes.fromhex("faf84258b23c46086a68d698ce4e3c32"), "big")

# ---------- Lay body HTTP giua nan nhan va C2 (ca truong data.data lan media.type) ----------
tshark = shutil.which("tshark") or r"C:\Program Files\Wireshark\tshark.exe"
out = subprocess.run(
    [tshark, "-r", PCAP, "-Y", "http && ip.addr==156.238.233.121",
     "-T", "fields", "-e", "frame.number", "-e", "ip.src", "-e", "data.data", "-e", "media.type"],
    capture_output=True, text=True, encoding="utf-8", errors="replace").stdout


def dec(b):
    return AES.new(KEY, AES.MODE_CTR, nonce=b"", initial_value=IV).decrypt(b)


def score(b):
    s = b[:400]
    return sum(32 <= c < 127 or c in (0, 9, 10, 13) for c in s) / max(len(s), 1)


def direction(src):
    return "C2->victim" if src.startswith("156.") else "victim->C2"


packets = []
for line in out.splitlines():
    p = line.split("\t")
    while len(p) < 4:
        p.append("")
    fr, src, raw_data, raw_media = p[:4]
    raw = raw_data or raw_media
    if not raw:
        continue
    try:
        body = bytes.fromhex(raw.replace(":", "").replace(",", ""))
    except ValueError:
        continue
    packets.append((fr, src, body))

print(f"Tong so goi co body: {len(packets)}")
big = sorted(packets, key=lambda x: -len(x[2]))[:15]
print("Cac goi lon nhat:")
for fr, src, body in big:
    print(f"  frame {fr:>6} {direction(src)} {len(body)} bytes")

# ---------- PHAN 1: cac goi giai ma ra chu doc duoc ----------
os.makedirs("dec", exist_ok=True)
print("\n##### READABLE PACKETS #####")
for fr, src, body in packets:
    if len(body) <= 20:
        continue
    cands = [(score(dec(body[o:])), o) for o in (0, 8, 12, 16, 20, 24) if len(body) > o + 16]
    if not cands:
        continue
    sc, off = max(cands)
    pt = dec(body[off:])
    open(f"dec/{fr}.bin", "wb").write(pt)          # luu moi goi de soi tay neu can
    if sc < 0.85:
        continue
    print(f"\n=== frame {fr} {direction(src)} len={len(body)} off={off}")
    print(pt.replace(b"\x00", b"")[:800].decode("latin1"))

# ---------- PHAN 2: quet sau (nhieu offset + base64) ----------
print("\n\n##### DEEP SCAN #####")
KW = (b"schtasks", b"scheduledtask", b"taskname", b"/tn ", b"/create",
      b"register-", b"\\tasks\\", b"-enc", b"frombase64", b"itaskservice")
b64re = re.compile(rb"[A-Za-z0-9+/=]{40,}")

for fr, src, body in packets:
    if len(body) <= 20:
        continue
    found = False
    for off in range(0, min(len(body) - 16, 64), 4):
        flat = dec(body[off:]).replace(b"\x00", b"")
        texts = [("plain", flat)]
        for m in b64re.finditer(flat):
            try:
                texts.append(("base64", base64.b64decode(m.group()).replace(b"\x00", b"")))
            except Exception:
                pass
        for kind, t in texts:
            low = t.lower()
            hit = next((k for k in KW if k in low), None)
            if hit:
                i = low.find(hit)
                print(f"\n--- frame {fr} {direction(src)} off={off} [{kind}] keyword={hit.decode()}")
                print(t[max(0, i - 200):i + 600].decode("latin1"))
                found = True
                break
        if found:
            break
```
